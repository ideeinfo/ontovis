登记附加配置源为 [ontovis-workbench-postgres.conf](../../deploy/ontovis-workbench-postgres.conf)。它显式指定 PG 后端和三个固定目录，只允许项目根、共享库根可写。分析附加配置见§5；原 base unit、GIS 环境和 Cloudflare 配置保持。当前前端与Nginx版本以最新执行记录为准，不能沿用历史发布配置覆盖。

运行账户仅有本库 CONNECT、两套 schema USAGE、登记四表及分析四表 SELECT、`project_workspaces` 的 INSERT/UPDATE，以及§5列出的分析最小写权限。表和 schema 归不可登录的所有者，服务无 DDL、DELETE、TRUNCATE、REFERENCES、TRIGGER 权限，也不能切换到所有者。公有 schema 和本库 PUBLIC 默认权限已撤销。核对 OntoBase 现有 ACL 后，该账户无业务表权限、建 schema 对象权限或可执行的业务 SECURITY DEFINER 函数；未修改 OntoBase 业务表或其权限。

角色属于共享实例，数据库 CONNECT 与业务表权限是不同层级。现有其他数据库的 PUBLIC CONNECT 策略未改，不把这次权限核对描述为网络或独立实例隔离。依据：[PostgreSQL 角色](https://www.postgresql.org/docs/16/sql-createrole.html)、[对象权限](https://www.postgresql.org/docs/16/ddl-priv.html)。

## 2. 仅项目登记阶段的备份与校验

**启用分析草稿后，本节旧命令会拒绝执行，改用§5整组备份；不能遗漏草稿修订。**

必须停止工作台写入，使用 PG 专用快照工具；旧 SQLite snapshot 会拒绝 PG 标记目录。下例在 153 root shell 执行，不开启 shell 跟踪、不输出环境变量。新目标必须不存在，目录名按本次操作确定。

```sh
(
cd /data/ontovis/workbench-current/code
set -a
. /data/ontovis/private/workbench-registry.env
set +a
q13_backup="/data/ontovis/output/q13-backup-$(date +%Y%m%d-%H%M%S)"
systemctl stop ontovis-workbench.service || exit 1
trap 'systemctl start ontovis-workbench.service' EXIT
/data/ontovis/runtime/registry-v1/bin/python -m tools.project_registry_runtime snapshot \
  --project-root /data/ontovis/private/workbench-pg-v1/project-spaces \
  --library-root /data/ontovis/private/workbench-pg-v1/workbench-library \
  --model-root /data/ontovis/private/workbench-pg-v1/workbench-model \
  --destination "$q13_backup" --service-stopped
)
```

成功回执给出独立保存的 `manifestSha256`。工具持有目录共享锁和 PG 所有权锁，在实际只读事务中取得登记，将其物化为 SQLite 登记，配回全部业务库和文件。应另保存回执并以该 SHA 使用 `tools.project_store_backup verify` 检查；清单存在本身不代表校验通过。凭据环境文件不进入数据备份，也不进入 Git。

## 3. 仅项目登记阶段的恢复和故障处置

**当前分析已启用，本节不再作为整组恢复步骤；必须使用§5，保留分析修订与请求回执。**

1. 保留当前完整 PG 配对快照，使用其外部 SHA 校验。运行期间发生过写入后，禁止直接切回旧目录或迁移前 B0。
2. 可用 `tools.project_store_backup restore-new` 将当前快照恢复为全新 SQLite 配对目录；也可用 `tools.project_registry_runtime activate-new` 恢复到新的自有 PG 库/空运行 schema 和全新目录。后者以受控的所有者连接离线建表，再授予上述最小运行权限；长期服务只读取专用账户配置。
3. PG 绑定包含三个绝对路径及目录 inode。目标必须在最终路径激活；禁止复制、重命名目录后修改标记来规避校验。恢复目标和原运行目录不能重叠。
4. 新目录核对原登记 UUID、项目范围、全部业务表摘要、固定文件及引用；再用真实用户重新登录核对当前源权限。标准恢复和 PG 恢复的合成权限验收不能替代这一项。
5. 修改附加配置指向新配对目录和对应后端，先校验配置再启动。SQLite 恢复仍使用兼容当前业务 schema 的代码；仅删除 PG 附加配置会重新指向旧数据，不能当作回退步骤。

连接丢失会拒绝登记操作，不自动重连或回退 SQLite。先诊断数据库和服务状态；重新启动之前确认没有第二服务持有目录/PG 锁。原会话在重启后失效，需要正常重新登录。

## 5. 分析草稿启用后的整组备份与恢复

Q-21 首期增加 `ontovis_analysis_v1` 四表，仍使用同一个 ONTOVis 独立库及既有服务账户。新增 systemd `analysis.conf` 仅配置非敏感 `ONTOVIS_ANALYSIS_STORE_ID`；它必须等于当前数据库的固定存储身份。角色不变：运行账户只读四表，可插入会话/修订/回执，仅可更新会话名称、进度、头修订和更新时间；没有历史更新/删除、DDL或所有者权限。

备份、初始化和恢复使用离线所有者连接，由既有私有配置在操作进程中注入 `ONTOVIS_MAINTENANCE_DSN`；不要输出或写入脚本。运行账户不因备份获得历史表的写权限。停止服务后执行：

```sh
python -m tools.analysis_workbench_backup snapshot --database-env ONTOVIS_MAINTENANCE_DSN \
  --project-root /data/ontovis/private/workbench-pg-v1/project-spaces \
  --library-root /data/ontovis/private/workbench-pg-v1/workbench-library \
  --model-root /data/ontovis/private/workbench-pg-v1/workbench-model \
  --destination "$new_backup" --service-stopped
python -m tools.analysis_workbench_backup verify --backup "$new_backup" --manifest-sha256 "$manifest_sha256"
```

使用153已安装的 `/data/ontovis/runtime/registry-v1/bin/python`。目标必须全新；保存外部摘要，完成后恢复服务。整组包含登记、全部业务SQLite/文件、分析四表及清单；不包含凭据。

恢复使用 `restore-new --database-env ONTOVIS_MAINTENANCE_DSN --backup "$new_backup" --manifest-sha256 "$manifest_sha256" --destination "$new_restore" --service-stopped`。此时环境变量必须指向新的自有目标库。恢复回执给出新的 `analysisStoreId`；将运行配置绑定到该ID及新配对目录，授予最小运行权限，完成真实账号回读后才能启用。不要复用部分失败目标，不要把旧工作台单独恢复后丢弃分析历史，不要在有新写入后直接回滚旧B0。

恢复消费者须沿用原私有项目/安装上下文配置；配置旧模型目录时不得遗漏该范围。配置值只经进程环境传入，不打印、复制到脚本或公开回执。

测试站启用、B0/B1/B2和恢复结果见[执行记录§99](../plans/开发执行记录.md#99-q-21本人分析草稿接入2026-10-26)。仍为单服务进程和有界测试容量，业务SQLite迁移及多进程运行继续后续。
