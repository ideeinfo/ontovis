# 模型格式与来源核验

核验日期：2026-10-20。本文记录 ONTOVis 模型输入、标识保留与转换的证据和限制，供产品及实施设计引用；不代替业务流程、权限合同或工程审核。结论分为官方格式能力、当前源码/样机事实和拟议产品约束，三者不能互相替代。

## 1. 当前输入范围

**仅 GLB 2.0 是 MVP 的正式运行时输入主路径。** IFC 支持通过离线、受控转换生成 GLB 与来源映射清单后导入；这不等于已经具有在线 IFC 上传转换服务。其他 CAD、BIM 或交换格式均不计入当前已支持格式。当前产品处于设计阶段，既有真实 GLB 样机不是正式模型管理功能。

| 格式 | 本次范围与建议 | 保留与验证边界 |
|---|---|---|
| 自包含 `.glb` | MVP 正式输入目标；配套可选 sidecar JSON | 验证容器与 glTF 版本、全部资源、必需扩展、单位/轴及节点清单。扩展名为 GLB 不代表绝无外部 URI |
| `.gltf`、`.bin`、纹理分离包 | 先在受控工具中整理成 GLB | 本期不承诺任意 ZIP、多入口或外链资源包导入 |
| IFC | 离线受控转换后导入；保留原 IFC、转换版本与 sidecar | 几何转换与 GlobalId/属性提取分别验证，不把 GLB 当作完整 IFC 数据库 |
| FBX | 预处理候选，不计入当前直接输入 | 验证自定义属性、层级、材质、动画、单位与轴；不能保证任意导出链无损 |
| RVT | 优先在源 Revit 环境导出 IFC，再按受控路径处理 | 原生 RVT 解析、许可证、导出版本与平台依赖不包含在 GLB 导入能力中 |
| STEP/IGES 等 CAD | 有实际样本后单独评估确定的转换路径 | B-Rep 网格化不保留参数化编辑能力；构件语义与标识需另行保留，不笼统承诺“支持 CAD” |
| OBJ/STL | 后续纯几何输入候选 | 不默认具备工程构件身份、业务属性或完整装配语义 |

glTF 是运行时资产交付格式，索引、场景树和属性约定用于加载与渲染。它不是源 CAD/BIM 数据库的替代品。依据：[Khronos glTF 2.0 规范](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)。

## 2. 标识语义：源对象、几何定位与业务实体

| 标识 | 语义 | 稳定性与约束 |
|---|---|---|
| `sourceModelKey` | 来源模型/模型谱系的身份，与源版本字段分开 | 区分两个项目或供应方中同名、同编号的模型；不能仅采用文件名 |
| `sourceElementId` | 来源系统中的元素标识，如 IFC GlobalId | 保存原值及 `sourceIdKind`；其稳定性取决于源系统与导出过程，不由 ONTOVis 凭名称推定 |
| `placementId` | 元素在装配或场景中的具体放置实例 | 同一模板或几何被多次使用时必须区分；不能把同机型多台设备合为一个实例 |
| `nodeIndex` | 指定 GLB 文件中 `nodes[]` 的数组下标 | **只在该文件版本内有效，绝不能作为跨版本稳定 ID** |
| `nodeKey` | 受控派生模型中维护的模型语义键 | 只有实际保留并通过唯一性检查才可用于迁移；提案别名并不天然稳定 |
| `entity_uid` | OntoBase 权威工程实体主键 | 来自有权限的服务端查询与核验，不能直接信任上传 `extras` 或 sidecar 声明 |
| RDS、显示名称 | 工程编码/匹配线索及显示文字 | 需结合项目、实例、编码语义与证据，不能替代业务主键 |

源对象关联至少以 **`sourceModelKey + sourceElementId + placementId`** 区分。若 IFC 已为不同构件实例分配不同 GlobalId，仍保留 placement 身份承接场景安装；若将同一教学模板放置成多台设备，则 placement 必须各自不同。`modelRevision/sourceRevision` 是版本引用，不应混入后再把结果宣称为跨版本稳定源标识。

运行时定位采用 `modelAssetId + modelRevision + file + nodeIndex`。一个业务构件可以对应多个节点；同一 mesh 被不同 node 或实例复用，不意味着它们属于同一个工程实体。Three.js 的运行时 `id/uuid` 也不作为工程持久化身份。

glTF 规范明确内部引用使用对应数组下标，名称不保证唯一；`extras` 为应用自定义数据，建议使用 JSON 对象，但不赋予其中字段稳定身份语义。以上跨版本约束是基于这些事实制定的产品规则。[索引与名称](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#indices-and-names)、[extras](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#reference-extras)

### 2.1 GLB 与 sidecar 的最小分工

建议在受控派生 GLB 的 `extras.ontoVis` 中保留 `nodeKey/sourceElementId/sourceIdKind` 等经过白名单校验的模型属性，便于拾取。项目权限、`entity_uid`、审核结论与发布修订保留在服务端绑定记录中，避免模板资产携带跨项目权威身份。上传内容中的业务 UID 只可成为待验证声明。

sidecar 是绑定到**同一个模型产物版本**的来源与定位清单，最少包括：

- 文件级：模型 ID/修订、源模型键/源修订、导出工具及版本、单位/轴、坐标变换修订。
- 元素级：源元素 ID 及类别、placement ID、节点定位数组、nodeKey 及其性质、显示名称、可选来源 RDS。
- 来源证据：源文件与版本、必要的出处引用；不把上传清单本身当作工程确认。

缺少源元素 ID 的旧模型可以浏览，也可以经人工建立本版本绑定；应明确标为“跨版本身份未建立”。不得以自动生成的数组序号、名称或包围盒哈希假装获得源系统稳定身份。sidecar 的来源对应关系和服务端业务绑定是两个不同事实。

### 2.2 Three.js 的实际属性承接

核验的 Three.js **r184** `GLTFLoader` 源码会把对象型 `extras` 合并到 `object.userData`，原始类型值则不按该方式承接。可将这一实现作为属性保留测试依据，但不能把它推定为所有工具链的共同保证。[r184 GLTFLoader 源码](https://raw.githubusercontent.com/mrdoob/three.js/r184/examples/jsm/loaders/GLTFLoader.js)

实际样机使用附件的 Three.js **r128**。其 parser association 结构与新版本不同；内部 parser 映射只能在锁定版本、经过测试的加载代码中用于当前文件节点定位，不能形成跨版本身份合同。正式产品 Three.js 版本尚需按项目依赖与目标设备测试决定，本文引用 r184 不表示已经选用或升级。

## 3. IFC、Revit 与 CAD/FBX 转换证据

### 3.1 IFC GlobalId 与转换结果必须分别核验

buildingSMART 定义 `IfcGloballyUniqueId` 为用于识别 IFC 对象的编码标识；`IfcRoot` 系列对象承载 GlobalId。它不同于 IFC STEP 文件中的 `#123` 实例行号，也不同于转换后 GLB 的 nodeIndex。源系统重建对象、重新分配 ID 或模型复制后的冲突，仍需识别。[buildingSMART GlobalId](https://standards.buildingsmart.org/IFC/RELEASE/IFC4_3/HTML/lexical/IfcGloballyUniqueId.htm)

IfcOpenShell 官方提供 GLB 几何序列化示例，并在该示例中设置 `use-element-guids=True`。但同站序列化选项页对这个开关列出的适用格式是 OBJ、DAE、STP、SVG，未列 GLB。**文档存在覆盖范围差异，不能只凭该开关宣称最终 GLB 必然按预期保存 GlobalId。**[几何序列化示例](https://docs.ifcopenshell.org/ifcopenshell-python/geometry_processing.html)、[序列化参数说明](https://docs.ifcopenshell.org/ifcopenshell/serialiser_settings.html#use-element-guids)

受控转换应锁定工具版本，同时提取 IFC GlobalId→输出几何对应关系，保存 sidecar，再检查最终 GLB 中的具体字段位置、值、数量与重复情况；名称中可能出现的编码、后缀或表示上下文不得靠固定截字符串猜测。属性与空间关系从 IFC 单独保存，不能因 GLB 可显示就视为全部继承。本次没有对实际 IFC 样本执行转换，因此该路径是有官方依据、仍需样本验收的离线导入方案。

### 3.2 Revit、FBX、CAD 的边界

Revit 官方列出 IFC、FBX 等导出能力；其 IFC 导出设置还提供将生成的 IFC GUID 写入元素参数的选项。建议在来源端保留该身份和导出配置，并用连续两次导出及构件增删改样本验证。不能由“Revit 可导出”推出 ONTOVis 可直接读取 RVT。[Revit 导出格式](https://www.autodesk.com/support/technical/article/caas/sfdcarticles/sfdcarticles/Revit-Export-format.html)、[IFC 导出设置](https://help.autodesk.com/cloudhelp/2025/ENU/Revit-DocumentPresent/files/GUID-E029E3AD-1639-4446-A935-C9796BC34C95.htm)

Blender 提供 FBX 导入与自定义属性选项，glTF 导出可将自定义属性写入 extras。但多边形网格、材质、层级、动画和扩展都有各自的转换规则，不能承诺 FBX→Blender→GLB 自动保留全部工程语义。转换配置和属性保留测试应随样本记录。[Blender FBX 4.4 手册](https://docs.blender.org/manual/en/4.4/addons/import_export/scene_fbx.html)、[Blender glTF 4.4 手册](https://docs.blender.org/manual/en/4.4/addons/import_export/scene_gltf2.html)

Open CASCADE 的 XDE 与 glTF writer 提供 STEP/IGES、装配结构、名称/颜色及网格输出的技术基础；这是未来受控 CAD 转换的候选能力，**不等于本项目已经支持所有 CAD 格式、版本、专有属性或构件标识**。[OCCT XDE](https://occt3d.com/dev/doc/overview/html/occt_user_guides__xde.html)、[RWGltf_CafWriter](https://occt3d.com/dev/doc/refman/html/class_r_w_gltf___caf_writer.html)

## 4. 压缩、优化与构件边界

| 技术 | 官方能力 | 本项目约束 |
|---|---|---|
| Draco | 对 mesh primitive 几何压缩；规范指出可能改变顶点顺序和数量 | 不沿用旧顶点/三角形序号映射。节点级标识是否保留应检查具体转换结果；不能笼统说压缩必然删除 node 身份 |
| Meshopt | 在 bufferView 层压缩几何、动画或实例数据 | 压缩本身不是跨构件合并；优化管线若另外重排/简化/合并，需单独验证 |
| KTX2/Basis | 纹理超压缩与运行时转码，可减少传输及纹理显存占用 | 不解决几何身份或 draw-call 问题；需配置对应转码资源并验证画质 |
| join/flatten | 合并兼容 primitive、改变层级以降低绘制开销 | MVP 禁止跨业务构件自动合并。只优化同一构件内的非交互细节，并验证拾取、隔离、动画与绑定覆盖 |

依据：[Draco 扩展](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_draco_mesh_compression/README.md)、[Meshopt 扩展](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Vendor/EXT_meshopt_compression/README.md)、[KTX2/Basis 扩展](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_texture_basisu/README.md)。Three GLTFLoader 分别要求配置 Draco、Meshopt 和 KTX2 解码/转码依赖；离线部署必须同时交付所需资源，不能暗中依赖 CDN。[GLTFLoader 文档](https://threejs.org/docs/pages/GLTFLoader)

glTF Transform 的 join 默认可合并不同节点，提供 `keepMeshes/keepNamed` 等控制；清理步骤也可能移除原有资源。不能直接套通用 optimize 默认配置后假设原节点与副文件仍然对应。[join 文档](https://gltf-transform.dev/modules/functions/functions/join)、[join 源码](https://github.com/donmccurdy/glTF-Transform/blob/main/packages/functions/src/join.ts)

## 5. 格式校验与换版验收范围

Khronos glTF Validator 能检查 JSON/GLB 结构、内部引用、缓冲区、部分图片与扩展，并输出统计和问题报告。它不证明工程对象身份、安装位置、映射正确性或产品性能达标。[官方 Validator](https://github.com/KhronosGroup/glTF-Validator)

本项目还需检查：

1. 必需扩展是否在锁定运行时支持范围内；外部资源是否全部满足自包含约束；单位、轴、原点与安装变换是否明确。
2. 源标识、placement 与 nodeKey 的完整性和重复情况；一个构件对应多个节点时是否完整覆盖；多个实例是否被错误合并。
3. 连续版本的新增、删除、拆分、合并、源 ID 重置、坐标变化与节点重排。旧 nodeIndex 不迁移；相同源标识只生成迁移候选，异常进入人工复核。
4. 优化前后的拾取、隔离、动画节点、包围盒和映射覆盖；材质压缩与几何压缩分别检查。
5. 发布版固定引用模型与绑定修订。旧会话保留旧版引用；不得因同名或空间接近静默切换到新实体。

这些是模型处理与版本验收约束；完整上传、审核、发布和权限流程由产品设计文档定义，本文不另建一套流程状态机。

## 6. 当前源码与实际样机边界

核验时的 OntoBase Web `package.json` 已有 React/Vite、React Flow、Radix 等依赖，尚未声明正式 Three.js、MapLibre 或 IFC 转换依赖。API/worker 已使用 FastAPI、MinIO、Redis；现有 `/api/v1/drawings/upload` 与 `/api/v1/source-files/upload` 仅接收 PDF，不能称为已存在的模型上传 API。上述存储与任务方式可以在设计中复用，但不表示模型业务已经实现。

**对象补建能力纠正：**当前人工对象创建入口为 `/api/v1/drawings/{drawing_uid}/object-locations`，源码要求图纸存在且 bbox 必填，动作语义为 `manual_bbox_create`。独立、无 bbox 的工程对象补建 API 是拟新增能力，不能写作“已有通用受控补建流程”。在该能力完成前，缺少柜级实体的模型关联保持待解析；不得绕过 OntoBase API 直接写库。

核验时本机代码来源（仅为证据，不作为 ONTOVis 构建依赖）：[Web 依赖](../../../OntoBase/apps/web/package.json)、[API 源码](../../../OntoBase/apps/api/ontobase_api/main.py)、[worker 源码](../../../OntoBase/apps/worker/ontobase_worker/main.py)。这些链接需相邻 OntoBase 工作区存在；公开格式结论使用本文官方 URL 独立追溯。

### 6.1 TU-3000 与 Demo-PDS 三柜事实

附件是 TU-3000 通用教学几何，不是 MySE3.0 工程的厂家 CAD/BIM；二者功能与安装关系未经确认。附件 56 个 GLB 共 23,810,164 bytes；齿轮整机 2,470 个节点、2,272 个 mesh 实例、113,804 个实例三角形。原文件未含动画片段，样机转子旋转由程序模拟。

| 示例目标 | 真实几何事实 | 必须保留的候选语义 |
|---|---|---|
| `=WEC+CN2` 机舱信号柜 | 指定齿轮整机版本的 controller nodes 1150–1166；sourceObjectId 402/403 只是主体/门的源 Three 对象编号举例 | `source_candidate`；不能将 sourceObjectId 或 nodeIndex 当作工程 UID |
| `=WEC+CN1` 机舱动力柜 | 用独立代理补模；原 converter 明确为变流器，不能强行等同动力柜 | `proxy_schematic`；尺寸与安装位置示意 |
| `=WEC+CT` 塔基控制柜 | 用独立代理补模；源整机 75.1 m 高平台柜不能冒充塔基柜 | `proxy_schematic`；安装关系待核验 |

三柜清单 1.1 的 `nodeKeyKind=proposed_semantic_alias`、`entityUid/projectId/tenantId=null`、`status=pending_entity_resolution` 应原样保持其语义。`source.controller` 及两个代理 nodeKey 是提案别名；不能自行升级为跨版本稳定键或已批准业务关联。清单中的 `entityUid` 是该演示 JSON 的字段名，业务事实仍以 OntoBase `entity_uid` 为准。

真实 WebGL 样机仅将三柜挂在 WTG-01：1 台精细主机 + 30 台背景，共 31 个可视风机；其余设备仅显示模拟监测状态。程序地形非 DEM。样机 34 项功能检查通过、0 脚本错误、0 外网请求，只证明所测离线交互；headless SwiftShader 短时 FPS、未做 LOD/合批的结果不代表产品性能验收。

附件未发现开放模型再利用许可，Three.js MIT 许可不能替代模型素材授权。原模型、教学文本与纹理不因本地技术验证而获得对外分发权；本参考文档不打包这些素材。
