# 模型与设备关联工作流

**ONTOVis V0.1 · 2026-10-20 · 完整工作流设计基线。** 本文与[主设计](ONTOVis产品与架构设计.md)配套；格式依据与官方来源见[核验记录](../references/模型格式与来源核验.md)。实际已实现的20MiB静态GLB上传与7号三柜演示关联见[上传切片](../plans/模型上传与演示关联切片.md)，不等于下文完整流水线已经落地。

2026-10-22新增待评审方案：[场景管理与模型实例统一实施方案V2](../plans/场景管理与模型实例统一实施方案.md)。统一项目模型资源、地形、场景放置、整设备关联与实例内部构件关联；解除当前固定单机/版本级绑定的实现限制。V2经国内平台对照补齐资源校准预览、使用去向和换版预览；模型角色可复用，实例UID与后续测点身份独立。该方案确认后先在现有MagicPath项目冻结页面与服务，执行状态见工作区交接。

## 1. 格式支持边界

| 文件类型 | 首期处理方式 | 用户看到的结果 |
|---|---|---|
| **自包含 `.glb`，glTF 2.0** | 正式模型上传入口；校验真实内容与扩展，不只检查后缀 | 处理后获得可浏览模型版本与构件目录，尚未自动绑定设备 |
| 同批 JSON 构件清单 | 推荐携带稳定源ID和构件分组；人工校核；与上传文件指纹匹配 | 身份质量、重复ID、缺失构件报告 |
| CSV 业务映射清单 | 可选批量提议格式，预览后生成绑定候选；不直接导入为正式关系 | 每行匹配依据、目标对象、冲突原因；所有行仍受权限约束 |
| `.gltf + .bin + 图片` | 首期提示预先导出自包含GLB | 不静默抓取外部资源；后续真实需求再加受控包导入 |
| IFC | 推荐先通过固定工具链离线转GLB，同时导出GlobalId/属性sidecar | 可上传派生GLB；UI不标成“原生支持IFC上传” |
| RVT、FBX、STEP/IGES等 | 由原建模软件/指定转换工具预处理；每种路径须样本验收 | 不承诺任意版本、层级、材质、动画或属性无损 |
| OBJ/STL | 首期不提供直接入口；后续可受控转换为几何预览 | 往往缺工程身份，不能因成功显示就认定可自动关联 |
| 3D Tiles、地形瓦片、PMTiles、GeoTIFF | 属于独立地理图层数据路径 | 不与设备GLB上传混为一个格式选项；Cesium仍为条件备选 |

glTF `extras` 可以携带自定义属性，名称不保证唯一，数组索引只在文件内部有效。Three.js GLTFLoader的属性导入是具体版本实现，需要锁版本测试，不能把运行时 `Object3D.id/uuid` 作为工程标识。[glTF索引与名称](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#indices-and-names)、[glTF extras](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#reference-extras)、[GLTFLoader](https://threejs.org/docs/pages/GLTFLoader)

## 2. 标识规则

| 标识 | 谁定义 | 唯一范围/用途 | 禁用方式 |
|---|---|---|---|
| `sourceModelKey` | 原建模来源或受控导出配置 | 同一来源模型连续版本的身份，区分不同文件/专业包 | 不只用可变文件名 |
| `sourceElementId` | 原建模系统，例如IFC GlobalId | `sourceModelKey + sourceElementId + placementId`，保留原始大小写和字符串 | 不用STEP行号、mesh序号、对象名称替代 |
| `placementId` | 源装配或受控转换过程 | 区分同一源部件在一个模型内部的多次放置；与整模型场景实例分开 | 不以本版本nodeIndex冒充跨版稳定放置身份 |
| `componentKey` | ONTOVis构件目录 | 语义构件键，可包含多个node/primitive；有稳定来源时持续追踪 | 无稳定来源时不得承诺跨版恒定 |
| `nodeIndex/primitiveIndex` | 本GLB结构 | 派生文件版本内的拾取/高亮定位 | 不能单独做跨版本或跨模型绑定键 |
| `sceneModelInstanceId` | ONTOVis | 区分同一机型模型在WTG-01/02等的放置 | 不同机位不能共用同一工程柜体实体 |
| `entityUid` | OntoBase | 工程对象主键，结合connection/projectCode解析 | 不在ONTOVis生成另一套同名“objectUID”；不重算其内部哈希 |
| RDS/名称/属性 | 工程资料/模型来源 | 候选匹配线索，需要命名空间、方面和实例范围 | 不自动唯一化，不剥离前缀后强行匹配 |

若模型包含属性 `ObjectID`、`externalId` 或 `GlobalId`，先在上传表单中选择**它是什么标识**：源构件ID、工程台账ID、RDS还是仅显示名称。只有存在已确认的命名空间/映射关系，才能连接到OntoBase。两个系统的字段同叫“对象ID”不代表值属于同一空间。

匹配规则固定为受控映射：`模型属性路径 → 标识scheme → 项目/实例范围 → OntoBase候选查询`。可从后台列出的属性中选择，不运行用户脚本或任意JSONPath/正则程序。字符串默认精确匹配；需要去空白等规则时预览原值与规范化值，检测碰撞，保存规则版本。标识大小写策略必须由源契约决定。

## 3. 版本内构件目录和sidecar

同一GLB内的重复装配使用独立 `placementId`；与整模型在地图上的 `sceneModelInstanceId` 共同确定最终放置。若源系统没有稳定放置标识，使用版本内构件键并标记不可自动迁移，不能把合法重复装配误判成同一设备。IFC实例GlobalId本身已区分放置时，也记录其来源约定。

一个柜体可以有门、框架、螺丝等多个网格；绑定的是语义构件而不是每个draw call。首期支持将一组明确节点归为一个构件，优化只能在该边界内合并。若父组与子组几何重叠且分别绑定不同对象，必须显式设置可拾取层级，或者在发布前消除重叠；不能让点击随机命中。

建议的JSON示例仅说明字段，并非真实项目导入内容：

```json
{
  "schemaVersion": "ontovis-component-map/0.1-proposal",
  "sourceModelKey": "demo-tu3000-geared",
  "sourceRevision": "attachment-20261004",
  "artifactChecksum": null,
  "coordinate": {"lengthUnit": "m", "upAxis": "Y"},
  "components": [
    {
      "componentKey": "demo.controller-cabinet",
      "keyStability": "version_local",
      "sourceElementId": null,
      "placementId": null,
      "sourceIdKind": null,
      "displayName": "机舱信号柜几何候选",
      "nodeIndices": [1150,1151,1152,1153,1154,1155,1156,1157,1158,1159,1160,1161,1162,1163,1164,1165,1166],
      "geometryQuality": "source_candidate",
      "claimedObjectRef": null
    }
  ]
}
```

以上节点号只对已核查的附件版本有效，checksum未填的示例不能发布。上传服务计算实际产物指纹并校验sidecar所属文件；源文件、派生文件分别记录，禁止把源nodeIndex直接用于处理后已重排的派生模型。

派生GLB可在 `extras.ontoVis.componentKey` 写入经校验的内部键，用于运行时拾取；模型内的 `claimedObjectRef` 只是一项声明，服务端重新解析项目和权限后才产生业务候选。不能将模型属性里的URL、脚本或HTML当可执行内容。

没有稳定源ID的旧模型仍可浏览并手工绑定，但 `keyStability=version_local`；新版本迁移必须复核。是否稳定来自导出与验证记录，不由字段名或AI猜测决定。

## 4. 最小持久化设计

以下逻辑表名为设计提案。JSON用于小规模配置，不意味着每个字段都要独立新表。

| 数据 | 主要字段 | 不可省略的约束 |
|---|---|---|
| `model_assets` | modelId、ONTOVis projectId、名称、用途、来源/许可、归档状态 | 一个项目范围；可复用模板与实际实例分离 |
| `model_versions` | versionId、modelId、原件/派生URI与指纹、处理状态、导出器/处理器版本、坐标与质量报告 | 产物不可原地覆盖；失败版本不替换已发布版本 |
| `model_components` | versionId、componentKey、sourceModelKey、sourceElementId、placementId、属性、node/primitive定位、bounds | 版本内key唯一；源标识＋placement重复进入冲突；同组多节点允许 |
| `model_processing_jobs` | jobId、versionId、阶段、attempt、leaseToken、错误、资源统计 | 幂等、重试不重复发布；隔离处理资源，不与识别任务抢同一无限队列 |
| `scene_revisions` | sceneId、revision、场站/坐标、modelInstances、visualizationRevision | 固定版本引用，expectedRevision并发控制 |
| `model_bindings` | bindingId、bindingRevision、sceneModelInstanceId、modelVersionId、componentKey、objectRef、状态、证据/审阅记录 | 发布绑定必须有核实工程引用与实例范围；草稿可为空 |
| `binding_reviews` | 目标binding、操作者、动作/原因、源版本、时间 | 追加记录，撤回不抹除审核历史 |

`objectRef`固定为受控连接标识、OntoBase项目代码、entityUid。对同一场景实例的同一构件，首期只允许一个主设备绑定；一个设备可由多个几何构件表示。柜内大量设备不直接占用这一主绑定，而是通过物理父链解析空间位置。

模型本身可在隔离预览区浏览，无需所有装饰件都绑定；正式场景只要求必需交互对象通过审核。背景/环境构件可显式标为“非工程绑定范围”，不降低关键设备映射覆盖统计的分母。

## 5. 上传与校验流程

### U1 选择项目与版本目标

用户选新模型或现有模型的新版本，填写名称、用途（场站低模/设备细模/环境）、来源与许可说明、单位/轴向、是否模板、源模型身份。权限由服务端验证，浏览器隐藏入口不构成安全保证。复制模型到另一项目是新资产/新授权，不自动复制原项目绑定。

### U2 上传原件与可选清单

已实现首切单GLB上限为20MiB，替代原200MB建议；新场景方案沿用该限额。受控JSON/CSV清单、上传会话和分段能力属于后续设计，不接受任意压缩包。未来采用分段上传时，完成动作需校验所有分段与归属；中断可重试，过期未完成数据按配置清理。实际样本较小时继续普通受控上传，不为断点续传建立平台。

校验实际魔数/MIME、总字节、GLB结构、JSON深度/属性长度、贴图尺寸、声明长度与实际文件、外部资源引用。自包含要求缓冲区和纹理在同一制品内；禁止处理器自动抓取上传文件指定的HTTP/file URI。未认可的必需扩展阻断处理；可忽略扩展必须记录影响。[Khronos glTF Validator](https://github.com/KhronosGroup/glTF-Validator)

### U3 隔离处理与报告

服务端排队：结构校验 → 属性/构件目录 → 几何统计与坐标检查 → 受控优化/派生 → 拾取键校验 → 缩略图/报告。后台按任务限CPU、内存与执行时长；取消后迟到产物不能成为可发布版本。

报告分别列出：格式错误、源ID完整率/唯一率、网格/三角形/材质/纹理数量、估计解码资源、bounds与单位、动画clips、缺纹理、节点对应关系和未支持扩展。性能通过真实目标设备评测，不以压缩后文件大小替代内存/FPS结论。

Draco、Meshopt、KTX2可在锁定解码器与离线资源后启用；它们不自动减少构件级draw calls。压缩/优化不得跨业务构件盲目合并；三角形级索引在重建后需要重新生成映射。旧附件有数千网格，低模/细模分开和构件内合批仍需保留。[Draco扩展](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_draco_mesh_compression/README.md)、[glTF Transform join](https://gltf-transform.dev/modules/functions/functions/join)

### U4 确认坐标和实例

glTF规范采用米制、右手系、Y向上。表单中的“源单位/轴向”记录来源与导出核验，不能仅把字段改成毫米/Z向上就改变GLB规范语义。错误导出需要受控归一化或显式校正变换，形成新派生版本后检查尺度/方向；规范化后的运行时GLB与安装变换分开记录。[glTF坐标与单位](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units)

地理锚点、水平/垂直基准、来源单位/轴向、规范化变换、实例放置变换分别保存。地形高程不能直接当基础设计高程；DEM插值变化不应让设备随LOD跳动。固定至少三个已知方向/位置控制点核验尺度、朝向和轴，实际精度阈值按模型用途确定。

模型导出版本一旦通过并被发布，变换更改生成新场景修订，不能悄悄修正原件。运动分组单独记录转轴、枢轴、方向与数据源；柜体、外壳和叶轮不能因场景节点父子误用一起转动。

## 6. 关联工作台：从属性到工程对象

### B1 定义候选规则

管理员选择已提取属性，说明它属于哪个命名空间。按以下顺序生成候选，所有结果仍需本次人工确认：

1. 同来源模型连续版本中已审核的 `sourceModelKey + sourceElementId + placementId` 映射，先迁移为候选。
2. 上传明确声称的OntoBase引用，经canonical解析、项目/实例和权限检查后生成候选；不信任文件声明。
3. 模型属性匹配 OntoBase 中已有且已确认的标识scheme/scope；多个结果显示歧义。
4. RDS/名称/类型/源层级与空间位置仅作辅助候选。显示具体依据，不以AI置信分数替代工程核验。

没有匹配不自动新建资产。柜级对象缺失时跳转 OntoBase **拟新增的独立对象建档流程**，建立后重新解析；当前已有图纸+bbox创建入口不满足此要求。

### B2 人工审阅

左侧为模型构件树与匹配队列；中间为模型预览/高亮；右侧为工程对象搜索、实例范围、原始属性、RDS和证据。顶部固定项目、模型版本、实例与发布状态；底部列“未匹配/唯一候选/多候选/身份失效/坐标待核验”。

单次确认必须能回答：这是哪一个模型版本/实例？几何表达哪类设备？工程对象是否柜级？是否同一实际机组？来源证据是否足够？代理柜体是否明确标识？审核者有无此动作权限？

可批量确认一组具有相同规则和充分证据的唯一候选，但必须逐项通过服务端校验；报告每项结果。存在重复ID、未知实例或缺柜体UID时不能批量“一键全绿”。

### B3 建立柜内设备关联

柜体绑定完成后，读取OntoBase的已确认子设备分页列表。内部设备没有几何时保持 `directBinding=null`，由`locateObject`返回祖先定位。页面区分：有独立模型、通过所属柜体定位、未建模且无可用祖先。选择一个子设备不会把当前柜体绑定改成子设备UID。

无物理归属的设备保留在“待归属”队列。不能因为其图纸在CN2文件中、与CN2有电气边或名称含CN2，就默认为柜内设备。安装树编辑由OntoBase完成。

### B4 预检与发布

校验对应项目/实例、对象生命周期、构件存在/唯一性、范围内必须三柜、坐标、模型处理状态、未完成审核、权限和expectedRevision。通过后创建不可变绑定修订并发布场景组合。模型上传成功、渲染成功、匹配唯一、人工审核、业务可用是不同状态。

运行时仅消费发布版，管理员可在独立草稿预览中试用候选；草稿预览不写正式告警定位。首期发布前人工复核必需三柜，未绑定背景可继续存在。原型中真实UID未核实，因此“发布”保持禁用并给出原因。

## 7. 状态与失败恢复

| 维度 | 状态 | 行为 |
|---|---|---|
| 上传/处理 | uploading → queued → validating → processing → ready；failed/cancelled | ready只表示技术可用；失败保留报告，重试产生新attempt |
| 单条绑定 | unmatched / proposed / ambiguous / needs_identity / reviewed / rejected / stale | reviewed记录人和证据；stale需重新审核；拒绝保留原因 |
| 绑定修订/场景 | draft → checked → published → superseded/archived | 发布组合原子切换，旧版可回退；退役不删除历史会话引用 |
| 使用精度 | direct_geometry / ancestor_proxy / annotation_proxy / unlocated | 与绑定状态正交，避免“已审核=有精确三维” |

任务重复提交以 `clientRequestId` 幂等；相同源文件可以复用处理产物，但不同项目权限与绑定仍分开。Worker租约失效后旧任务不能提交；解析失败与身份失败分别重试。服务端版本冲突返回可读差异，禁止最后写入者无提示覆盖已审核内容。

## 8. 模型换版与工程变化

| 变化 | 迁移结果 | 审核动作 |
|---|---|---|
| 仅nodes重排，稳定源ID仍唯一 | 可重建版本内定位，生成继承候选 | 检查数量/分组/几何差异后批准新修订 |
| 没有稳定ID，名称/位置相似 | 建议候选，不继承已审核状态 | 人工选择与证据校验 |
| 源构件或内部放置拆分/合并 | 一对多/多对一差异组 | 明确哪些几何属于同一设备，重新确定主绑定 |
| 删除已绑定构件 | 对应新版本绑定缺失 | 阻断必须项发布或明确取消其要求，不能留幽灵高亮 |
| 源ID重用、重复、来源模型变化 | 冲突 | 不以相同字符串继承旧设备 |
| 坐标/单位/轴变更 | 所有相关放置需核验 | 控制点与定位验证，未通过不发布 |
| 子设备换柜 | 直接柜体绑定不变，祖先定位随有效期变化 | 查询树版本；历史回放按原时态，不在模型中批量重绑子设备 |
| 对象合并/退役/撤权 | canonical候选或失效 | 保留旧引用与原因，停止失效导航，审核后新版本生效 |

换版时旧场景仍服务，差异工作台并排显示新增/删除/变动/不变构件及受影响绑定。发布后保留旧版本及会话引用；有保留引用的制品不得被普通清理任务删除。安全撤权优先于历史可访问性，保留历史记录不等于继续授权访问文件。

## 9. 测试数据与规模验收

真实性验收用核实后的三柜及真实子设备集合；另建明确标识的合成规模夹具，例如一个柜体500子设备、两台实例复用同GLB，验证分页、重复报警聚合、祖先解析和无N+1请求。500是测试规模目标，不能在产品画面宣称为Demo-PDS实际设备数。
