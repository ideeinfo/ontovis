# 工单工作流与分析复用设计

V1 · 2026-11-11 · 用户方向已明确，本文为下一阶段设计基线，尚未实现或部署。实施顺序见[重构计划](../plans/工单工作流重构实施计划.md)。

## 1. 产品职责与覆盖关系

工单负责从发起、受理、处理到完成归档的业务过程，管理处理人员、文本记录及相关文档、照片。分析画布负责证据组织、知识图谱查询、故障诊断、排查建议和分析修订。分析独立存在，可供多个工单引用。

本设计覆盖旧[项目演示工单闭环](../contracts/项目演示工单闭环契约.md)与[助手工单联动](../contracts/分析助手与工单联动契约.md)中“在每张工单内编辑假设、结构化排查方案、逐项填写结果、满足诊断清单后复核关闭”的后续建设方向。旧文档继续描述已上线版本和历史验收，权限、固定引用、幂等、审计与备份要求继续有效。

| 工单内完成 | 分析画布内完成 |
|---|---|
| 发起、分派/受理、转交、完成、归档、必要时重新处理 | 汇集图纸、手册、照片、趋势、报警、工单及图谱证据 |
| 查看推荐分析，人工选择本单采用的分析版本 | 比较资料、提出假设、核对缺口、形成排查处置建议 |
| 记录实际做了什么、观察到什么、处理结果和待办说明 | 新建分析，或基于已有固定分析修改另存 |
| 上传/引用附件，查看记录和依据历史 | 保存分析修订，设置故障码/适用范围及项目复用范围 |

工单不再提供另一套诊断编辑器。工单中的排查建议以所采纳分析的只读内容呈现，实际排查处置通过文本记录表达。完成工单表示人员提交了本次处理结果，不等于系统确认根因、解除报警或完成现场控制。

## 2. 主流程与最少必填

主流程为 **发起并提交 → 待处理 → 处理中 → 已完成 → 已归档**。新建表单的未提交内容属于本机草稿，不增加业务状态。默认取消独立的“诊断中 / 排查中 / 待复核”步骤，不引入审批流程配置器。

| 阶段与操作 | 必要输入与行为 | 下一状态 |
|---|---|---|
| 发起并提交 | 当前项目、标题、问题说明。设备/对象、来源报警、故障码、处理人和附件按来源带入或补充。手工工单可无故障码，未能确认设备时保留待定位说明 | 待处理 |
| 受理 / 开始处理 | 有处理权限的人员认领，或由有分派权限的人员明确指定处理人。记录实际开始人和时间 | 处理中 |
| 处理过程 | 可查看或采纳分析、进入画布、追加文本和附件。保存记录后状态保持。转交记录前后处理人和说明 | 处理中 |
| 完成处理 | 处理人员提交非空处理结果。可直接采用已有的一条已保存处理记录作为结果，不要求重复填写。所选附件须完成关联，未完成上传可重试或明确移除 | 已完成 |
| 归档 | 有归档权限的人员确认，保存完成时的记录、附件与分析引用索引 | 已归档 |

完成处理不以“所有分析假设已证实”“全部建议已逐项填写”“必须采纳一个分析”或“必须上传照片”为前置。无须诊断的普通任务、没有推荐分析的任务也能正常处理。分析中的不确定性、模拟标记及现场限制在完成后继续显示。

已完成和已归档的工单默认只读。需要补做或纠正时，有权限的人员通过“重新处理”填写原因，追加新的处理周期，旧完成/归档记录和当时的依据保持。重复或误建单可用“作废并归档”记录原因及处置结果“未执行”，保留原编号，不能伪装成已完成现场处理。该例外不增加日常必经步骤。

首批不增加排班、SLA、工时、备件、审批模板或外部派单。处理权和归档权使用明确的权限判断，不能通过移除旧复核步骤放宽为任意成员可关闭。

## 3. 处理人员的工作路径

1. 从工单或报警进入，查看问题、设备、当前处理人及已有记录。系统在当前授权项目内自动查找相关分析，页面显示命中依据。
2. 已有合适分析时，打开固定版本核对适用对象和建议，点击“采纳此分析”。本单记录该分析的固定版本，多个工单可采纳同一版本。
3. 没有合适分析时，点击“新建分析”，带入本单固定快照、设备、报警和已有附件引用。时间窗沿用来源或画布默认值，不要求进入助手时先选择。
4. 已有分析需要调整时，点击“基于此分析修改”，以该固定版本创建独立画布草稿。修改后“另存并用于本单”，得到新的分析 ID 和来源追溯，再关联本单。
5. 回到工单，对照所采纳分析的建议实施处置，追加“检查了什么、结果如何、做了什么”的文本，可附照片或文档。一次记录可描述多个建议，不强制拆成结构化检查项。
6. 写明最终处理结果并完成，随后归档。处理过程若发现新的证据，可再次进入画布分析，显式更换本单采用的版本并保留更换历史。

保存分析、关联工单、采纳为本单依据分别产生真实回执。可合并为一个用户操作，但遇到部分失败必须准确说明已完成项并只重试未完成项。返回工单不会自动完成、归档或重新调用模型。

## 4. 自动推荐与人工采纳

### 4.1 推荐范围和排序

推荐读取当前账号可见的项目分析目录，包括本人保存的分析和明确设为项目可参考的固定版本。检索不受当前画布卡片、当前工单是否含历史工单卡、或当前三分钟趋势窗口限制。跨项目复用本批不自动开放。

复用分析继续使用现有画布目录，不另建方案库。画布保存版本中维护故障码语境、适用对象/型号、可读的分析摘要和排查建议。已有分析缺这些字段时保留原版，由有权人员补充后另存新修订。若建议来自助手回答，须明确整理到画布并保存，不能在推荐时直接读取私人对话充当共享分析内容。

优先使用故障码及其来源/型号语境，再比较工程对象身份、设备型号/项目采用配置、适用范围和模拟/真实标记。相同数字但属于不同厂商或代码体系的故障码不视为等价。缺少代码体系或设备适用性时保留“同码候选，适用性待核”，不猜成匹配。

同一分析的多个可参考版本默认合并成一个候选，展示最新的可用共享版或本人保存版，另可查看旧版。明确不适用、回收或已撤回共享的版本不进入新的默认推荐。候选按适用程度排序，同等条件下优先最近维护版本，提供分页和“查看全部”。无需模型即可完成首轮精确推荐，模型可按请求解释差异，不能改变匹配身份。

每个候选显示分析标题、版本、简要建议、同码/同设备/同型号等匹配依据，以及已知的不适用项或缺口。没有结果、读取失败、无权和只取得部分结果分别呈现。处理人员始终可新建分析或继续记录，推荐失败不阻塞工单流转。

### 4.2 关联、采纳与换版

- **关联参考**表示可以查阅的分析。关联不等于处理人员已经采用其建议。
- **采纳此分析**表示本单当前选用的主要处置参考。每单同一时点一个主要分析，可保留其他关联参考。
- 采纳记录包含工单身份及修订、分析身份/修订/摘要、采纳人、时间和可选说明。建议取自固定分析内容，不再次复制成工单诊断方案。
- 采纳不改变分析的工程确认状态，不将候选根因提升为已确认，不自动把建议标为已执行。
- 原分析更新后，本单继续指向原版本。用户查看差异后才能“换用此版本”，原采纳记录保留。撤回本单采纳只影响本单当前指向。
- 采纳不要求原分析已经用于关闭工单。处理结果也不自动作为推荐算法中的“根因正确”评价。

### 4.3 修改另存与共享边界

从工单打开已采纳或推荐分析时默认只读。选择“基于此分析修改”创建独立副本，保留来源分析 ID、固定修订及摘要，不改原分析或其他工单引用。副本带入本次工单上下文，原事件、旧趋势、工单及附件继续标为历史证据，不能改标签冒充本次数据。保存成功前不写入本单采纳。

复用优先沿用现有画布的另存与固定证据能力。现有分析按本人隔离，项目成员之间共享固定分析是本次待补能力，不能仅去掉 owner 条件。由分析所有者明确将所选保存版本设为“供本项目参考”，可在首次关联/采纳面板中一次完成范围选择，不增加独立审批流程。后续修改不会自动共享新版本。

共享范围包括所选固定画布的分析内容、可展示的建议和资料引用，不包括私人助手对话、其他草稿或未选版本。读取画布、建议摘要、卡片、来源和附件均重新核权。共享分析不授予底层资料的新权限，失权内容及由其派生的摘要不得从快照或推荐摘要泄露。受限内容显示授权允许的占位，不能将权限裁剪后的内容冒称原完整快照。

撤回共享会停止新推荐/采纳，旧工单保留原采纳事件和固定身份。历史全文仍按当前权限读取，不因曾经采纳就绕过撤权或自动换成别的版本。对外部分析修改另存也须先有读取与派生权限。

## 5. 文本记录与附件

### 5.1 处理记录

主界面只提供一个文本输入和附件入口，可选填写发生时间，保存时自动记录操作者、录入时间、工单修订及当时采纳的分析版本。允许记录检查、观察、处置、补充说明，不要求先选记录分类。

已保存文本的更正以新修订留痕，界面显示最新内容并可展开修改历史。处理结果可引用其中一条保存记录。附件和文字作为人员记录保留来源，不由 AI 补造测量值、现场动作、签名或完成事实。完成/归档后的补充走“重新处理”，本批不增加另一个归档编辑入口。

### 5.2 上传及已有关联资料

工单支持“上传附件”和“引用已有资料”，可把附件关联到整个工单或某条处理记录。文件内容及版本使用 OntoBase 文档/照片的正式受控能力，Vis 管理工单关联和展示，不建立第二套工程资料权威库，不直接写源端数据库。

实施前核对源端当前上传、固定读取及成员授权接口。资料上传与人工业务记录不依赖 OCR、知识提取或模型运行成功。上传完成仅代表文件已存妥，关联成功才显示“已加入本单”。源端上传成功而工单关联失败时保留文件身份和回执，重试关联，避免重复上传或删除已有文件。

附件列表显示名称、类型、上传者、录入时间、固定版本及预览/下载状态。照片可显示人工注明的拍摄时间，EXIF 时间不能自动当作现场事实。复用已有资料不复制文件内容，替换文件生成新版本并显式关联，旧工单和分析引用不随之换版。移出本单只撤销当前关联并留痕，不删除源文件或其他工单的附件。

文件类型、大小、预览能力和上传恢复方式按核实的源端限制在页面提前说明。失败、取消、断网重试与权限变化保留逐文件状态，文件名/正文不能成为助手的操作指令。工程资料权限、下载权限与当前项目范围都由后端复核。

### 5.3 画布中的工单资料卡

用户补充明确：**向分析画布添加工单，主要为了参考该单的处置过程记录和结果。** 此能力继续作为九类资料卡中的工单类型保留。当前工单和历史工单均可按权限加入，未完成或未采纳分析的工单也可参考。加入只建立固定资料引用，不修改工单、不自动把当前分析设为该工单的处置依据。

卡片首先显示工单编号、设备/故障码、状态、引用修订与模拟/真实来源标记，正文优先展示“处理结果”和最近处置记录。展开后按时间阅读完整记录、操作者、发生/录入时间及该记录的照片/文档附件。未完成或尚未登记结果时明确显示当前状态，不将建议、空字段或归档状态推成处理成功。完整内容按页读取，不能只保留一段无法追溯的摘要。

工单曾采纳的分析作为“当时的处置依据”单独展示链接，按需打开原固定版本。其建议不混入“实际处置记录”。卡片主视图不再使用假设数量、排查步骤完成数或旧诊断结论作为核心内容，旧记录仍在历史区只读可查。

分析助手读取该卡时，提供实际记录正文或可定位的片段、处理结果、记录身份/版本/时间以及相关附件的固定身份。回答可引用到具体记录和附件，并区分人员观察、人员报告的处置结果、原分析建议及尚未读取的文件。资料预算不足时说明省略范围并支持继续读取，不把未读说成“工单没有处置记录”。同码工单的历史处置可供比较，但人员记录或“已完成”状态本身不证明根因相同。

卡片固定到加入时的工单修订。原工单新增记录后提示可查看进展，由用户比较后显式载入新修订并保存画布，原分析历史仍可回看旧记录。画布删除工单卡不删除原工单；移除本单的分析关联也不影响其他画布中的工单引用。附件随卡片固定版本读取，仍须当前授权。

分析与工单允许双向引用，但读取不递归展开“分析→工单→原分析”。默认只读取工单自身的过程、结果和附件索引，已采纳分析保留固定链接。用户明确需要读取该分析时按身份/修订去重并计入预算。由分析建议复制而来的文字保留来源，不当成另一份独立验证；新登记的实际观察和处置结果才作为新增人员记录供分析参考。更新证据产生新的分析修订或另存分析，不能反向改写原建议来制造验证闭环。

## 6. 界面与设计规范

正式页面继续使用现有 MagicPath「ONTOVis 产品设计」，版本入口见[设计索引](MagicPath交互设计.md)。本次只更新文字方案，页面稿及服务契约在实施首步冻结。

- **工单列表**保留项目、搜索、状态和处理人筛选。行内给出编号/标题、设备/故障码、状态、处理人、更新时间，已归档可筛选查看。新建工单入口清晰。
- **工单详情**顶部为标题、状态、设备/故障码和处理人，右侧一个当前阶段的主操作。默认“处理记录”展示问题摘要、最近记录和固定输入区。
- 详情用“处理记录 / 相关分析 / 附件”三个同级页签。相关分析先显示已采纳版本，再显示推荐；默认页保留一个紧凑的“相关分析”摘要和入口，便于开始处理时发现推荐。
- “相关分析”只提供查看建议、采纳、基于此分析修改、新建分析及必要的版本比较。诊断编辑、知识图谱探索和多资料排版统一打开原分析画布。
- “查看分析”复用资料卡详情窗口宽度，正文分层、有清晰段落和来源入口。标题、版本和必要操作固定，长内容独立滚动，避免窄弹窗堆叠整篇文字。
- 旧“本单诊断排查 / 来源参照图 / 四项检查 / 建议采纳条目”收纳进按需展开的历史区，日常处理页不再展开这些编辑控件。
- 保持灰绿深浅主题、正文 13px、说明 11px，中文工程名称可换行，原 Logo 比例不变。报警与对象选中沿用橙色，成功动作不借用报警样式。窄屏同顺序纵向显示，不依赖横向滚动操作。
- 显示保存中、失败、版本冲突、结果待确认、只读与来源受限的必要状态。普通操作不弹连续确认，采纳面板只核对目标、版本和必要共享范围。

## 7. 权限与助手职责

以下为待实施业务权限，不能视为当前已存在的角色。当前工单写入主要受管理员限制，必须显式实现并验证处理权限后才能供普通处理人员使用，不能把所有项目成员提升为管理员。

| 主体 | 可做事项 | 约束 |
|---|---|---|
| 有建单权限的人员 | 发起、提交工单及初始附件 | 当前项目和有权引用的对象/文件 |
| 本单处理人员 | 受理、保存处理记录/附件、采纳分析、完成处理 | 同时具备工单处理权限且是当前处理人，受状态与版本约束 |
| 有工单管理权限的人员 | 分派/转交、必要时处理、归档、作废及重新处理 | 明确对象与原因，留存审计，不获得源端工程修改权限 |
| 项目只读成员 | 查看有权工单、记录、分析和附件 | 每项内容依自身授权读取 |
| 后台工程助手 | 检索、解释推荐、完整编辑有权画布；按明确指令准备或保存文本/附件关联 | 与手工操作共用权限、字段、状态、版本和真实回执 |
| 驾驶舱工程助手 | 查询工单、相关分析与资料，解释建议，带问题和目标转后台 | 不写画布、处理记录、附件关联、采纳或状态 |

“采纳此分析”、完成、归档、作废与重新处理由人员在业务界面明确执行，助手可预填目标和内容。助手整理文本仅使用用户提供或可追溯的记录，不代表操作人员完成了现场工作。后台助手不会将建议自动写成诊断清单，也不会因推荐命中就代人采纳。

所有写入由后端核对当前身份、项目、具体权限、工单状态和期望修订。重复提交回读同一次结果，冲突保留草稿，结果未知先查原回执。来源变更只阻止相应的新采纳或附件引用，不阻止人员保存与受限来源无关的处理记录。

## 8. 数据保留与旧版过渡

逻辑上补充工单处理记录、附件固定关联、分析采纳/更换记录、共享固定分析范围及派生来源。它们属于现有工单和分析模块的扩展，不新建通用流程引擎或分析平台。具体表/接口待实施前核对后冻结，本文没有声明新的接口已上线。

旧 `open` 投影为待处理，`diagnosing` / `investigating` 投影为处理中，`review` 投影为处理中并保留“旧版待复核”历史说明，`closed` 投影为已完成而非已归档。这是新界面的兼容读法，不批量重写原行、事件、固定快照及摘要。

旧固定快照按原序列化结构和原摘要读取。新展示状态和扩展字段放在独立的当前响应或新版本结构中，不给旧快照补空字段或重算摘要。归档保存固定索引并延续既有文件保留规则，不复制或重新上传一套附件；历史可追溯与当前读取权限分别检查。

用户在新流程中首次操作旧工单时，按原修订检查并追加明确的流程升级记录。旧工单无处理人时由认领/分派补齐，不从历史最后操作者猜测。旧关闭单没有结果正文时仍可作为历史完成单查看/归档，记录“旧版未登记”，不能补造处置结果。

旧假设、排查结果、照片引用、助手采纳记录及其原修订只读保留。需要继续分析时可由用户显式导入新画布，区分旧建议和已记录的现场观察。旧分析关联仍为参考，不能自动升级为本单“已采纳”。删除画布卡片不删除工单，移除工单关联不删除分析。

发布前以最新在线数据备份并在隔离环境演练迁移、恢复与旧引用回读。回退须采用兼容新数据的代码，不用旧备份覆盖用户新处理记录。新流程启用后，旧客户端的诊断清单/复核写动作对已升级工单返回明确刷新提示，不能绕过新状态流或把记录写入隐藏字段。

## 9. 设计验收主线

核心场景是两张相同故障码工单共用分析 A 的固定版本。第二张工单发现新的情况后，从 A 修改另存为 B，只将第二单改采 B。两单各自记录处置、上传附件并完成归档，第一单仍回看 A，A 的原文、版本、其他引用和私人对话保持。

同时验证工单卡实际过程/结果读取、处置进展显式换版、双向引用不重复佐证，以及无故障码任务、无分析也可完成、同码不同型号、共享与撤权、上传部分失败、并发采纳、保存成功但关联失败、旧单继续处理及驾驶舱只查询。具体用例、依赖、完成门见[实施计划](../plans/工单工作流重构实施计划.md)。
