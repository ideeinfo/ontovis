# ONTOVis 产品与架构设计

**V0.2 · 2026-10-20 · 架构提案，生产能力尚未实施。** 当前整体入口见[ONTOVis整体设计](ONTOVis整体设计.md)；本机目录采集已落地，不能据此推断产品服务已实现。 承接 2026-10-19 Wind Cockpit V1.2，正式工作名称改为 ONTOVis。本文及配套工作流、配置中心、排期共同构成增补；旧版中与本版冲突的模型管理、绑定、设备层级和新增范围排期以本版为准。原有地图路线、Canvas、实时接入与受控 Agent 原则继续保留。

## 1. 决策摘要

1. **独立同级项目与 Git 仓库**：本地 `/Users/diwei/项目2026/OntoVis`，不放入 OntoBase 的 apps，也不建立嵌套 Git。用户已创建独立 GitHub 主仓库 [ideeinfo/ontovis](https://github.com/ideeinfo/ontovis)，接手时已关联本机 `origin`；尚未首个提交或推送。
2. **模型管理放在 ONTOVis**：模型原件、版本、转换产物、构件目录、模型实例、几何绑定、审核与换版都由 ONTOVis 负责。它直接服务于三维渲染，不要求 OntoBase 安装 Three.js 或模型转换器。
3. **设备主数据和物理层级放在 OntoBase**：允许无图纸、无几何的设备；将控制柜与内部器件建立经核实的物理包含关系。图纸识别、RDS、电气连接和资料证据继续由 OntoBase 管理。
4. **一个柜体绑定柜级设备，柜内子设备通过层级定位到柜体**：几何绑定数量不随内部设备数量膨胀；没有独立几何就标明代理定位，不能给数百设备伪造精确坐标。
5. **首期正式模型上传为自包含 GLB 2.0**，可伴随受控 JSON/CSV 构件标识清单。IFC/CAD/FBX/RVT 先离线导出或受控转换为同一入口；直接转换服务属于后续范围。
6. **配置采用固定业务表单与发布版本**：项目、模型、场景、数据映射、告警、AI 策略和访问控制有明确权限与校验，不建设通用低代码平台或工具市场。

## 2. 产品定位与仓库组织

ONTOVis 面向风电、油气、铁路等工业资产，以空间场景和设备为入口，把监测事件、工程资料与 AI 分析放到同一工作空间。首期只用 Demo-PDS/三柜验证跨行业共用机制，不宣称本轮已完成三个行业的数据适配或业务验收。

两类工作空间：运营人员使用三维驾驶舱和分析 Canvas；数据管理员使用项目配置、模型库、绑定工作台和配置发布。配置入口放在 ONTOVis 的项目设置内，业务用户不必看到转换器、坐标矩阵或模型服务地址。

```text
项目2026/
├── OntoBase/            # 工程知识底座，保持既有仓库与原始资料
└── OntoVis/             # ONTOVis 产品的独立本地 Git 项目
    ├── README.md
    ├── AGENTS.md
    ├── assets/brand/    # 用户 Logo 副本
    ├── docs/design/    # 维护中的产品、工作流、配置设计
    ├── docs/plans/     # 范围与排期
    ├── docs/references/# 源码审计和公开格式依据
    └── output/         # 本机 HTML、原型、截图、归档；不入 Git
```

将来实现时按具体纵向切片建立 React/Vite Web、FastAPI API 和独立后台 Worker；现在不预建空应用、SDK 包、连接器注册中心或共享组件发布平台。若两产品确有稳定重复组件，可再提取版本化共享包；当前采用相同开源控件与分层约束，避免复制整个业务 Feature。

## 3. 模型管理归属比较与推荐

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| 模型、构件绑定全部放 OntoBase | 数据目录集中 | 把大文件处理、渲染派生格式、实例/LOD/场景发布耦合到识别与知识底座；ONTOVis发布受影响 | 不推荐首期 |
| 设备、层级、模型全部放 ONTOVis | 单产品开发可快速闭环 | 重复设备身份和工程关系，图纸/知识与模型可能各有一套事实 | 不推荐 |
| **工程事实归 OntoBase，模型与空间表达归 ONTOVis** | 业务事实唯一，三维可独立演进，支持多行业 | 需要稳定对象解析、层级查询、权限和引用生命周期契约 | **推荐** |

用户可从 ONTOVis 的设备层级页跳转到 OntoBase 编辑。未来如确需内嵌编辑，仍调用 OntoBase 的受控写接口，由 OntoBase 授权、校验和审计；不能在 ONTOVis 保存另一套可写父子表。首期不做双端同一事实编辑与冲突合并。

## 4. 权威数据边界

| 数据/能力 | 权威写入系统 | 另一端的使用方式 |
|---|---|---|
| 项目工程身份、对象 UID、名称/分类/标识 | OntoBase | ONTOVis 只读引用，显示来源版本；本地场景标签不改主名称 |
| 对象物理父子关系、有效期、证据 | OntoBase | 按权限查询子树、祖先和变更版本；不由模型树或RDS自动反推 |
| 功能、位置、产品视角与电气关系 | OntoBase | 分栏展示；电路允许环，不能套用物理树防环规则 |
| 图纸、文档、照片及工程证据 | OntoBase | 授权读取原始定位，固定文件版本；本期沿用原05的已有资料/照片引用，新增照片上传归档另行估算 |
| 模型文件、模型版本、构件目录、处理任务 | ONTOVis | OntoBase 对象页可给深链入口，首期无需新增3D模型后台 |
| 场景实例、坐标、几何绑定、人工代理例外 | ONTOVis | 引用 OntoBase 对象，不复制设备事实；自身有版本和审核 |
| 测点与外部对象映射、展示告警规则 | ONTOVis | 保留源系统标识、质量、原始级别，不修改源SCADA告警 |
| 分析会话、Canvas、AI策略/运行审计 | ONTOVis | 引用工程证据；AI判断不能直接写回工程事实 |
| 用户身份与项目授权 | 统一身份部署方案＋各系统服务端 | ONTOVis权限必须与OntoBase可达范围求交；不能复制共享签名密钥冒充SSO |

跨系统工程引用使用 `ontobaseConnectionId + projectCode + entityUid`。`ontobaseConnectionId` 为部署内受控连接标识；项目代码使用当前 OntoBase 契约，不杜撰已有全局项目 UUID。若将来提供不可变 projectId，通过明确迁移契约更新。ONTOVis 自身 `projectId/sceneId/modelId` 是本产品主键，与 OntoBase 项目代码分开。

## 5. 设备层级：新增什么，保留什么

### 5.1 源码事实

`asset.entities` 已能存没有几何的工程对象，但当前人工新增主要依赖图纸与 bbox；已有局部图谱 `PART_OF` 用于端子归属，尚不是可维护的物理安装树。存在对象合并记录，不存在成熟的外部 canonical 解析合同。详细文件与行号见 [现状审计](../references/OntoBase现状与改造清单.md)。本次静态阅读不证明开发服务器已部署或鉴权已通过。

### 5.2 最小物理树

```text
试点场站（工程上下文）
└── WTG-01（实际设备实例，需现场/台账核实）
    ├── CN2 机舱信号柜（柜级对象，有候选几何）
    │   ├── 控制器（独立对象，可无几何）
    │   ├── 开关（独立对象，可无几何）
    │   └── 柜内仪表（独立对象，可无几何）
    ├── CN1 机舱动力柜（柜级对象，示意代理几何）
    └── CT 塔基控制柜（柜级对象，示意代理几何）
```

此树是设计示例，不是已核实的 Demo-PDS 运行库对象。名称、RDS或页码不能证明实体已经建档。控制柜外的温度传感器，即使接线接入CN2，也不能因此成为CN2的物理子设备；它属于实际安装位置，电气连接单独保留。一个测点/信号也不必等同一台物理设备。

拟新增最小数据：`asset.physical_containments`（设计名，未迁移），包括 `project_code, installation_context, parent_entity_uid, child_entity_uid, status, valid_from, valid_to, evidence_refs, revision, recorded_at, actor`。从父到子统一表达“物理包含”；若需要“安装于位置”则使用独立位置引用，不再叠加第二套含义相近的父树。

约束与写入流程：

- 只允许同一项目、同一实际安装上下文中的物理实例关联；禁止把模板与实例混成一棵树。
- 同一时间每个子设备最多一个有效物理父级；根设备可以没有父级。半开有效区间避免交界时间重复归属。
- 禁止自指、祖先循环与跨实例串挂；事务内锁定受影响安装上下文并检查，不能只做前端检查。
- 草稿候选经有权限人员确认后生效，保存依据、操作者和原因；证据不足保持未归属。RDS/名称/图纸结构只生成候选。
- 移装关闭旧有效区间、创建新关系；事件回放按事件时间取树，当前视图按当前树。未知历史只能说明“不掌握当时安装关系”。
- 批量导入先校验同一批次产生的环、重复父、缺失实体，再一次受控提交；行级错误报告可下载。不会通过部分无提示成功破坏安装树。
- 柜体缺失时由 OntoBase 独立建档，来源标记人工/导入与证据；不要虚构图纸bbox才能创建对象。

### 5.3 模板与实例

机型模型可复用，设备身份不可复用。例如将一个机型模板放置31次时，应得到31个 `sceneModelInstanceId`（规则示例，并非现有样机组成；当前样机实际为1台精细整机＋30台独立背景简模）；每台设备及柜体须有各自已核实的工程引用。将一套未确定实例范围的 Demo-PDS 资料应用于所有风机，只能是带标签的演示配置，不能发布为31台真实设备的绑定。

批量实例化只能提议“同一构件语义映射到各实例对应柜级对象”；每个实例解析与检查唯一性。首期支持单机三柜，批量整场迁移和批量实例主数据创建列后续。

## 6. 物理层级与几何绑定如何协作

| 概念 | 例子 | 保存位置 |
|---|---|---|
| 工程对象 | CN2柜、柜内控制器 | OntoBase `entityUid` |
| 物理关系 | 控制器包含于CN2柜 | OntoBase 已确认层级及版本 |
| 模型构件 | 同一柜体的16个网格归为一个语义构件 | ONTOVis 本模型版本的构件目录 |
| 场景实例 | WTG-01的该模型放置实例 | ONTOVis 场景版本 |
| 直接绑定 | WTG-01/CN2构件 → CN2工程对象 | ONTOVis 已发布绑定版本 |
| 祖先定位 | 控制器 → CN2 → CN2构件 | 查询时解析，不生成控制器自己的假网格绑定 |
| 人工代理例外 | 无祖先几何时，标明由某场景标注点表示 | ONTOVis 单独审核；首期可不启用人工例外编辑 |

定位分为live与history两种明确模式。live：授权解析当前对象 → 查询当前场景修订中该实例的已发布直接绑定 → 无直接绑定时沿当前已确认物理祖先链查最近可见绑定。history：输入固定sceneRevision、modelVersion/bindingRevision，以及hierarchyRevision或事件asOf时间，按对应历史父链与绑定定位；缺少当时层级/场景版本时返回“无历史位置/未定位”，不能回退到当前树或最新模型。两种模式无结果均保留对象卡与可访问资料。一个对象有多个有效几何表示时优先当前场景/实例，再按明确主表示或让用户选择，不能随机跳机组。

返回 `selectedObjectRef, locatedObjectRef, locationMode, resolutionMode, resolvedAsOf, sceneRevision, hierarchyRevision, bindingRevision, modelVersionId, sceneModelInstanceId, componentKey, reason`。`locationMode` 至少区分 `direct_geometry / ancestor_proxy / annotation_proxy / unlocated`；几何可信度另用 `source_verified / source_candidate / proxy_schematic`。即使是直接绑定，也可能只是示意柜体，两个维度不能合并成一个“已绑定”绿灯。

用户选控制器后，右侧继续显示控制器资料，中心高亮CN2并显示“定位到所属机舱信号柜；控制器未独立建模”。点击柜体默认选柜级对象，可展开“内部设备”；不同时选中其所有子设备。

报警仍挂在实际子设备上。柜体聚合显示“可见范围内有N条活动报警”，按源事件去重，支持最大严重度/计数规则；不能据子设备报警宣布柜体整体故障。未知质量、失联与报警状态分开编码，隐藏无权对象时不得泄露其数量、名称或最高严重度。

## 7. 系统结构与技术栈

```text
浏览器：ONTOVis React/Vite
  ├─ MapLibre：地球点位、区域DEM、独立影像、低模场站
  ├─ Three.js：独立设备细模、构件拾取、动画
  ├─ React Flow：分析Canvas、资料与假设卡片
  └─ 项目配置/模型库/绑定审核：同一对象选择与权限状态
              ↓ 授权API / SSE
ONTOVis FastAPI 模块化服务
  ├─ 场景、模型/绑定、配置版本、会话与Agent
  ├─ 受控后台处理任务 → 隔离Worker → MinIO模型与派生物
  ├─ PostgreSQL（自身业务数据）、Redis（任务/短期状态）
  └─ 受控连接 → OntoBase API / 一个监测源 / 只读工单源
OntoBase
  └─ 稳定对象、物理层级、资料证据、图谱、权限、合并/退役
```

保留 MapLibre 首选、Three.js 细模、Cesium 条件触发路线。三级尺度始终在同一SpatialWorkspace/viewport内连续推进；全球/风场保持地图实例，近景需要独立Three画布时，预热并匹配锚点/屏幕投影后短时交叉淡化，不打开弹窗/新窗口。返回恢复相机、选择、图层和调查时间；只允许交接期间短时双渲染，不机械复制裸相机矩阵。详见[连续导航](全球风场风机连续导航设计.md)。区域DEM与影像独立获取，真实项目AOI、地理坐标与高程基准必须核实。公开30m级地形不能用于柜内器件定位或风机基础精确测量。

模型格式转换、优化和派生在后台/独立Worker完成；浏览器按需解析运行时GLB，仍需锁定版本的几何解码器与纹理转码器，适用部分交给浏览器Worker。浏览器不在打开驾驶舱时做CAD等大文件转换；渲染库按路由加载。当前TU-3000附件无动画clips的事实保留，转子动画由经核实的运动组和轴定义驱动；动画仅为表现，不推导真实转速。AI不逐帧操作模型、不接收每条实时消息。

权限是交集：`用户在ONTOVis的能力 ∩ OntoBase项目/对象资料授权 ∩ 场景发布范围`。不得使用超级服务账户返回用户不可见资料。对模型整体文件存在保密分区时，MVP以整模型/场景访问范围为边界；已经下载的GLB无法靠隐藏网格保密，应拆分模型资产或拒绝分区发布。

## 8. 对接合同与生命周期

以下是**拟议操作名**，不是已存在URL，也不要求建立通用SDK框架：

| 权威方 | 必需操作 | 关键合同 |
|---|---|---|
| OntoBase | resolveObject / getObject | 输入工程引用，返回canonical UID、生命周期/实例范围、权限、版本；合并/退役/删除不静默消失 |
| OntoBase | listObjects / listChildren / getAncestors | 服务端游标分页、项目/实例/类型过滤、物理关系状态/有效期；禁止全量加载后前端分页 |
| OntoBase | createIndependentObject / reviewContainment | 允许无图纸bbox、expectedRevision、来源/依据、同项目防环、审计；首期在OntoBase界面操作 |
| OntoBase | listEvidence / getAuthorizedFile / getBoundedGraph | 来源版本/定位、有效期、权限；图谱电气关系与物理树分开 |
| ONTOVis | createModelVersion / processModel / inspectComponents | 上传身份与校验、异步任务、不可变产物、错误报告 |
| ONTOVis | proposeBindings / reviewBindings / publishSceneRevision | 候选/冲突、人工审核、工程身份复核、固定版本、乐观并发 |
| ONTOVis | locateObject / aggregateVisibleAlarms | 直接/祖先代理/未定位、去重、当前授权范围、不宣称精准几何 |
| ONTOVis | saveConfigDraft / validateConfig / publishConfig | 固定表单类型、差异、权限、版本、发布范围与回滚 |

跨服务不做分布式事务。绑定发布先读取权威对象/层级版本并记录核验时刻，再在 ONTOVis 原子发布；响应中保留版本引用。若校验后工程事实变化，后续读取重新校验关键引用并将绑定标为待复核，不能保证远端事实永不改变。首期用有界批量查询和定期校验即可；无已有可靠事件机制时，不假装已有实时订阅总线。

对象合并：解析原UID得到新canonical候选，保留原绑定与来源、进入复核，不能把相似名称当合并。对象退役：现行场景提示失效，历史会话仍可展示当时版本及当前权限。对象删除/撤权：停止新查询与导航，清理对应缓存，不显示原缓存资料。OntoBase必须补齐跨产品引用的保留/退役规则，避免删除图纸时连带硬删仍被使用的对象。

## 9. 最小发布与审计

ONTOVis以场景发布版本固定 `modelVersion + modelInstancePlacement + bindingRevision + visualizationConfigRevision`，分析运行另固定 `agentPolicyRevision + evidenceSnapshot + hierarchyRevision/asOf`。不用一个全局版本号锁住所有项目，也不单靠前端 localStorage 保存工程配置。

发布门：授权通过、模型处理可用、构件身份与版本一致、范围内关键三柜绑定已审核、坐标有效、必须项未缺、无冲突、引用对象未失效、可见范围满足模型保密边界。允许环境背景构件未绑定，但必须区别“无需绑定”与“遗漏绑定”。

审计记录上传、处理、绑定提议/确认/撤销、版本迁移、配置发布/回滚、权限变更与Agent工具调用；字段至少有项目、操作者、时间、目标版本、前后差异、原因和关联任务。文件原件与凭据不写入普通审计日志。

## 10. Demo-PDS验证闭环

1. 核对运行库实际项目代码、导入修订、柜级实体及单机/模板范围。现有三柜清单 `entityUid/projectId = null` 保持待核实，不导入为真实绑定。
2. 在 OntoBase 建立/确认 CN2、CN1、CT 柜级对象和各自真实子设备；图纸结构只作候选证据。抽查至少每柜三类已存在子设备（实际缺某类则记录，不编造）。
3. 使用 TU-3000 教学模型：controller几何仅为CN2候选；CN1与CT用独立示意代理。两种机型工程等价性未核实，页面始终保留示意/待核验标记。
4. 模型构件直接关联柜体，点击内部设备经已确认父链定位到柜体；从柜体可查看分页子设备、图纸定位和证据。
5. 回放一个明确标记为模拟的子设备报警，确认柜体汇总与对象详情不混淆；接入真实源后仍保留质量/时间和实际对象身份。
6. 换模型版本、更换父级、对象合并、撤权、任务失败和绑定冲突分别验证。失败不可用旧缓存伪装成功。
